# P2：Decode CUDA Graph

P2 在 P1 的显式 `AttentionMetadata`、fast KV 写入和静态 `_DecodeBuffers` 之上，
把 decode 的整段 forward 捕获成 CUDA Graph，按 batch-size bucket 回放。prefill
继续 eager；decode 的 Python/launch 开销因此大幅下降。

## 1. 设计

### Batch 分桶

默认 bucket：

```text
1, 2, 4, 8, 16, 32, ..., max_num_seqs
```

实际 batch 向上取整到 bucket，padding 行用占位数据填满。例如 batch=3 使用
bucket=4，只取前 3 行 logits。

### Padding 的安全处理

CUDA Graph 的输入 shape 固定，所以 padding 行也必须执行完整的 forward。为了
避免 padding 写坏真实请求的 KV：

- `Runner.allocate_kv_cache` 在 graph 模式下额外分配一个 **pad block**；
- `BlockManager` 仍然只管理用户请求的 `num_blocks`，pad block 永远不参与调度；
- padding 行的 `slot_mapping` 指向 pad block，`context_lens=1`，`block_tables[0]`
  指向 pad block；
- padding 行的 token/position 用 0，输出 logits 被丢弃。

代价是一个 block 的 KV（block_size=256、Qwen3-0.6B 约 28 MB）和每个 bucket 的
logits 输出 buffer。

### 静态输入

每个 bucket 有自己的 `_DecodeBuffers`：

```text
input_ids      int64 [bucket]
positions      int64 [bucket]
slot_mapping   int32 [bucket]
context_lens   int32 [bucket]
block_tables   int32 [bucket, num_blocks]
```

每步 decode：

1. 原地填充 pinned CPU staging；
2. `copy_(non_blocking=True)` 到固定 device buffer；
3. `graph.replay()`；
4. 从 graph 的静态 logits buffer 取 `[:real_batch]`，再 argmax / sample。

### Slot 索引必须在图内重算

`CachedAttention` 用 `metadata.slot_indices()` 把 slot 转成 `(block, offset)`。
如果这些索引在 capture 前被缓存，replay 时会用 capture 时的旧值，导致 KV 写错位置。

做法：

- warmup 使用一个 metadata 对象，让它提前完成 kernel/allocator 预热；
- capture 使用一个**全新的** metadata，`_slot_block_size` 为空；
- `slot_mapping.long()`、除法和取模因此被捕获进图；
- replay 时这些 kernel 读取新的 slot buffer，更新图内的 `blocks/offsets` buffer，
  后续 28 层的 KV 写入都使用更新后的值。

### 捕获时机

`ModelRunner.allocate_kv_cache` 在绑定 KV cache 后立即捕获所有 bucket：

- 先 `RotaryCache.ensure(device)`；
- 用 side stream warmup 两次；
- `torch.cuda.graph(graph, shared_pool)` 捕获 `model.forward + compute_logits`；
- 所有 bucket 共享 graph pool，输出 logits 各自保留。

捕获失败会显式报错，不会静默退回 eager。

## 2. 结果

RTX 4060 Laptop / Qwen3-0.6B bf16 / block_size=256 / num_blocks=64 /
max_num_seqs=64 / cold cache。三种模式是互斥的：

- eager：P1.8 的默认路径；
- compile：decode-only `torch.compile`；
- graph：decode CUDA Graph（eager 捕获）。

| workload | eager tok/s | compile tok/s | graph tok/s | graph vs compile |
| --- | ---: | ---: | ---: | ---: |
| single-short | 69.5 | 89.2 | **110.4** | +23.8% |
| batch8-short | 497.5 | 576.0 | **678.1** | +17.7% |
| batch32-mixed | 875.3 | **928.3** | 917.8 | -1.1% |
| long-prefill | 52.5 | 56.5 | **64.4** | +14.0% |
| shared-prefix | 534.7 | 620.4 | **691.6** | +11.5% |

TPOT：

| workload | eager | compile | graph |
| --- | ---: | ---: | ---: |
| single-short | 14.3 ms | 11.0 ms | **8.8 ms** |
| batch8-short | 14.7 ms | 12.2 ms | **10.0 ms** |
| batch32-mixed | 16.0 ms | **14.0 ms** | 14.3 ms |
| long-prefill | 14.4 ms | 12.9 ms | **10.7 ms** |
| shared-prefix | 14.7 ms | 12.5 ms | **11.0 ms** |

解读：

- **低/中 batch（1–8）收益最大**：decode 的 launch/Python 开销占比高，graph 把
  每 token 的 kernel launch 从约 1,800 降到约 230；
- **batch32 上 compile 略快**：GPU 已经接近计算受限，compile 的算子融合比
  graph 的纯 launch 消除更有价值；
- **long-prefill 的 TTFT 基本不变**：prefill 仍是 eager；提升来自 decode 段的
  TPOT；
- graph 与 compile 当前互斥；后续可以把“compile 后的 forward”再捕获成 graph，
  但需要处理 compile 内部的 graph break/内存分配。

### Profiling

single-short，8 个 decode token：

| 指标 | eager | compile | graph |
| --- | ---: | ---: | ---: |
| `cudaLaunchKernel`/token | 1,838 | 354 | **234** |

### 显存

graph 模式：

- KV cache：1,792 → **1,820 MB**（pad block）；
- single-short 峰值：2,963 → **3,115 MB**；
- batch8：3,004 → **3,156 MB**；
- batch32：3,288 → **3,440 MB**；
- long-prefill：3,050 → **3,202 MB**。

增量约 150 MB，来自 pad block、graph pool 和各 bucket 的 logits 输出。

## 3. 使用

Python：

```python
from microinfer import LLM
from microinfer.config.engine import EngineConfig

llm = LLM.from_pretrained(
    "/path/to/Qwen3-0.6B",
    device="cuda",
    dtype="bfloat16",
    block_size=256,
    num_blocks=64,
    engine_config=EngineConfig(
        max_num_seqs=64,
        max_num_batched_tokens=8192,
        use_cuda_graph=True,
    ),
)
```

CLI：

```bash
python -m microinfer --model /path/to/Qwen3-0.6B \
  --prompt 'Hello' --max-tokens 8 --greedy \
  --block-size 256 --num-blocks 64 --use-cuda-graph
```

Benchmark：

```bash
python -m bench.bench_offline --model /path/to/Qwen3-0.6B \
  --engine microinfer --workloads single-short,batch8-short \
  --runs 3 --warmup 1 --block-size 256 --num-blocks 64 --use-cuda-graph
```

`bench/run_all.py`、`bench/ablation.py`、`bench/profile_runner.py` 也支持
`--use-cuda-graph`。

## 4. 约束

- 仅支持 CUDA；
- 需要 FlashAttention 分页 decode 路径：
  - FP16/BF16；
  - `block_size % 256 == 0`；
  - `head_dim <= 256` 且 `head_dim % 8 == 0`；
- 当前与 `use_compile` 互斥（`EngineConfig` 会报错）；
- 只捕获 decode；prefill 仍 eager；
- `max_num_seqs` 决定 bucket 数量；bucket 越多，logits buffer 和捕获时间越大；
- 重建/重新绑定 KV cache 会使旧 graph 失效，Runner 会清空 graph；通过
  `allocate_kv_cache` 重建时会自动重新捕获。

## 5. 正确性验证

- `tests/integration/test_cuda_graph.py`：
  - 同一模型权重下 graph vs eager，batch=3 padding 到 bucket=4，context length
    不同，输出 token 完全一致；
  - 直接构造 `use_compile + use_cuda_graph` 会报错。
- 真实 Qwen3-0.6B 额外手工验证：
  - batch=3、prompt 长度 7/20/33，graph 与 eager 8 个贪心 token 一致；
  - prompt 250 + 16 tokens，跨 256 block 边界，graph 与 eager 完全一致；
  - `Hello` 的贪心 token 与 HF Transformers 一致。
- `pytest -q`：**283 passed, 1 skipped**（P2 新增 2 个集成用例）。
- `ruff check microinfer tests bench scripts`：全绿。
