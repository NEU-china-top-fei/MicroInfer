# P4：混合调度、前缀缓存与 OpenAI 服务

P1–P3 把单步执行做快了，但引擎仍然是“一个大 batch 跑完再处理下一批”。P4 补齐
推理服务需要的调度、流式输出、取消和可观测性：

- decode 优先的混合 batch，长 prefill 不再整段阻塞正在生成的请求；
- 前缀缓存 LRU 淘汰、O(1) 反向索引和命中/淘汰指标；
- `AsyncEngine`：单步循环 + per-request 流式队列 + 取消 + 背压；
- OpenAI 兼容 FastAPI 服务：completions/chat/SSE/health/metrics；
- 并发 64 请求的吞吐与 P99 数据。

## 1. 混合 batch 调度

### 1.1 旧行为的问题

旧调度器先排 prefill，只有 waiting 为空才排 decode。一个 2048-token 的新请求
会连续占用多个 prefill step，期间所有正在 decode 的请求都停住，表现为 ITL
出现秒级尖峰。

P4 的 `Scheduler.schedule()` 改成：

```text
1. 先给 running 队列里的请求各排 1 个 decode token（受 token budget 限制）；
2. 用剩余 budget 从 waiting 队列排 prefill；
3. 如果两者都有，标记为 mixed step。
```

decode 请求按 round-robin 轮转：本步被服务的请求移到 running 队尾，避免
`max_num_batched_tokens` 小于 running 数量时固定饿死队尾。

相关代码：`microinfer/engine/scheduler.py`。

### 1.2 mixed step 怎么执行

混合 batch 不强制 decode 走 prefill kernel。`LLMEngine.step_events()` 把
scheduled 请求拆成两组：

```text
decode_seqs  -> Runner.run(..., is_prefill=False)  # CUDA Graph / compile
prefill_seqs -> Runner.run(..., is_prefill=True)   # eager varlen
```

两组分别执行，再按原 scheduled 顺序合并 token。这样 mixed step 的 decode 仍然
享受 P1–P3 的 fast path，而不是为了拼成一个 batch 退化到 prefill 布局。

### 1.3 公平性与 prefill chunk 上限

只做 decode 优先会让新请求等很久，而且一个 4096-token 的 prefill chunk 仍会
在一个 step 内阻塞 decode。P4 增加：

- `max_num_prefill_tokens`（默认 512）：单步 prefill 的最大 token 数；
- `mixed_batch=False`：回退到 pre-P4 的 prefill-first 策略，用于 A/B；
- `Scheduler.stats()`：waiting/running、prefill/decode/mixed step 数、preemption 数。

`max_num_prefill_tokens` 越小，decode 的 ITL 尖峰越低，但 prefill 被切成更多
step，吞吐和 TTFT 会变差。第 5 节给出 256/512 的对照。

### 1.4 抢占

保留 P1 的 recompute 抢占，并新增 `num_preemptions` 计数。decode 缺块时仍然
抢占 running 队尾，释放 KV 后重新 prefill；新的调度器会在 preemption 之后继续
尝试排 waiting，避免“KV 已释放但这一步没有可执行请求”。

## 2. 前缀缓存 LRU

`BlockManager` 原来用 FIFO free list，eviction 时还要扫描整个 hash 表删除
stale entries。P4 改为：

1. **Lazy LRU heap**：free block 的 `(last_used, block_id)` 入堆；分配时弹出
   最小项，stale entry 直接丢弃，`_free_blocks` set 是唯一真相；
2. **O(1) 反向索引**：`block_id_to_hashes` 记录每个 block 发布过的 hash；复用
   时只删除该 block 自己的映射，不再全表扫描；
3. **lookup touch**：`can_allocate` 命中前缀时更新 block 的 recency，真正实现
   “最近使用”的语义；
4. **指标**：`prefix_cache_hit_tokens`、`prefix_cache_hit_blocks`、
   `prefix_cache_evictions`，通过 `BlockManager.stats()` 暴露。

代码：`microinfer/engine/blockmanager.py`。

新增测试 `test_free_blocks_are_evicted_lru`：三个 free cached blocks，访问其中
一个后分配两个新块，验证被淘汰的是另外两个最久未使用的块。

## 3. AsyncEngine

文件：`microinfer/engine/async_engine.py`

### 3.1 线程模型

模型 runner 是同步的，并且拥有 CUDA state。`AsyncEngine` 只保留一个 step task：

```text
asyncio event loop
  add_request/abort  ── lock ──> scheduler
  step task          ── lock ──> asyncio.to_thread(engine.step_events)
  per-request queue  <──────────  updates
```

- `asyncio.Lock` 保证 scheduler 修改和模型执行不并发；
- `asyncio.to_thread` 把同步 `step_events` 移出事件循环；
- 每个请求一个 `asyncio.Queue`，消费者只拿到自己的增量事件；
- idle 时等待 `asyncio.Event`，避免忙轮询。

### 3.2 流式与 detokenizer

`LLMEngine.step_events()` 返回每个 scheduled 请求的累计 completion token 和
finish reason。`IncrementalDetokenizer` 解码累计 token，只发出新增文本：

- 不拼接单独 token 的 decode 结果，避免 UTF-8 跨 token 被拆坏；
- 未完成时丢弃末尾的 `�`，等下一个 token 补齐；
- 如果 tokenizer 修正了已发出的前缀，退化为发送修正后的尾部（流式协议无法撤回）。

### 3.3 取消、背压和释放

- `abort(seq_id)`：调用 `scheduler.abort`，释放 KV，向队列发 `finish_reason="abort"`
  的终止事件；
- 背压：`max_waiting` 控制 active + queued 请求数，超过时抛 `BackpressureError`，
  HTTP 层返回 429；
- `release(seq_id)`：消费者读完终止事件后清理 per-request bookkeeping；
  `AsyncEngine.stream()` 自动释放。

## 4. OpenAI 兼容服务

文件：`microinfer/serve/`，依赖为可选 extra：

```bash
pip install -e '.[hf,serve]'
python -m microinfer.serve --model /path/to/Qwen3-0.6B \
  --block-size 16 --num-blocks 1024 --use-cuda-graph
```

端点：

| 端点 | 说明 |
| --- | --- |
| `GET /health` | 引擎状态、队列长度、KV 使用率、last_error |
| `GET /metrics` | Prometheus text：请求数、TTFT/TPOT histogram、KV/前缀缓存 gauge |
| `GET /v1/models` | 单模型列表 |
| `POST /v1/completions` | 文本/ token prompt，支持 batch 和 SSE |
| `POST /v1/chat/completions` | 使用 tokenizer 的 chat template，支持 SSE |

流式示例：

```bash
curl -N http://127.0.0.1:8000/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Hello","max_tokens":16,"temperature":0,"stream":true}'
```

服务层还实现了 `stop` 字符串的 hold-back buffer：不会把半个 stop 字符串发给
客户端；命中 stop 后截断文本、终止请求并返回 `finish_reason="stop"`。

`/metrics` 的关键指标：

## 5. 性能

环境：RTX 4060 Laptop 8 GB / Qwen3-0.6B bf16 / block_size=16 / CUDA Graph。
在线 benchmark 不经过 HTTP，直接驱动 `AsyncEngine`：

```bash
python -m bench.online --model /path/to/Qwen3-0.6B \
  --requests 64 --prompt-len 128 --output-len 16 \
  --max-num-seqs 64 --max-num-batched-tokens 4096 \
  --max-num-prefill-tokens 512 --block-size 16 --num-blocks 1024 \
  --use-cuda-graph
```

### 5.1 64 请求同时到达

| 策略 | output tok/s | TTFT p50 | TTFT p99 | TPOT p50 |
| --- | ---: | ---: | ---: | ---: |
| 混合 batch（split 执行） | 1060.8 | 500.0 ms | 684.4 ms | 29.9 ms |
| prefill-first A/B | **1098.1** | **494.7 ms** | **658.9 ms** | **29.2 ms** |

所有请求同时到达时，prefill-first 略快约 3.4%：此时没有“正在 decode 的老请求”
需要保护，mixed 的两次 runner 调用反而多一点开销。

### 5.2 晚到的长 prefill：真正的收益

先提交 16 个长输出请求（output=64），200 ms 后到达 8 个 2048-token prompt：

| 策略 | output tok/s | 老请求 ITL p99 | 老请求 ITL max | 晚到请求 TTFT p99 |
| --- | ---: | ---: | ---: | ---: |
| 混合 batch，chunk=512 | 424.5 | **103.8 ms** | **103.8 ms** | 2852 ms |
| prefill-first，chunk=512 | **435.7** | 1098.4 ms | 1098.4 ms | **2783 ms** |
| 混合 batch，chunk=256 | 393.5 | **62.8 ms** | **62.8 ms** | 3086 ms |

结论：

- 长 prefill 到达时，旧策略让正在 decode 的请求停顿 **1.1 秒**；混合调度把
  尾延迟尖峰压到 **104 ms**，代价是吞吐 −2.6%、晚到 TTFT +2.5%；
- `max_num_prefill_tokens=256` 可以把尖峰压到 63 ms，但吞吐再降约 7%；
- 这是一个可调的延迟/吞吐旋钮，而不是固定的“混合一定更快”。

### 5.3 离线回归

P4 调度器对现有离线 workload 基本无回退（block16 graph）：

| workload | P3 | P4 |
| --- | ---: | ---: |
| single-short | 112.5 | 113.1 |
| batch8-short | 676.9 | 681.9 |
| long-prefill | 65.0 | 64.0 |

long-prefill 的 TTFT 从 167 ms 变成 176 ms，是因为 2048-token prompt 现在按
512-token chunk 执行；换来的是 decode 期间更可控的尾延迟。

## 7. 限制与下一步

- mixed step 是 decode/prefill 两次 runner 调用，不是单个 fused mixed-attention
  kernel；真正的 fused kernel 可以进一步消除这次拆分开销。
- 异步执行使用一个 `to_thread` worker；模型本身仍单进程、单卡。
- 服务未实现 `top_p`、`logprobs`、tokenizer 级 stop token、认证/限流和
  OpenAI 的完整参数集。
- 前缀缓存已 LRU，但 waiting 队列还没有按前缀相似度排序；swap-to-CPU 抢占也未实现。
- 指标是进程内内存状态，重启清零；生产环境应接 Prometheus + 持久化。
- P5 可做 speculative decoding 或更深的 paged attention kernel；P6 做 LICENSE、
  CI、打包和发布。

## 8. 面试追问

1. **为什么要 decode 优先？**
   decode 的每个 token 都是用户正在等待的增量输出；prefill 是批处理工作。
   先排 decode 可以避免新来的长 prompt 让所有活跃请求停顿。
2. **混合 batch 为什么把 decode 和 prefill 分开跑？**
   两者 attention 布局不同：decode 是一行 query + paged KV，prefill 是 varlen
   query。分开跑可以保留 decode 的 CUDA Graph/compile，不必退化到 prefill kernel。
3. **`max_num_prefill_tokens` 的作用？**
   限制单个 step 的 prefill 工作量，控制 decode 的 ITL 尖峰；越小越平滑，
   但 prefill 吞吐/TTFT 越差。
4. **LRU 为什么用 lazy heap？**
   堆提供 O(log n) 取最久未使用块，删除时只标记 set，弹出时校验 stale entry；
   避免每次分配扫描 free list 或整个 hash 表。
5. **前缀缓存的反向索引解决什么？**
   block 复用时要删除旧 hash；正向表只能全表扫描。反向 `block_id -> hashes`
   让删除只与该 block 有关，通常是 O(1)。
6. **AsyncEngine 为什么不用多个 worker 并发 step？**
   模型 runner 和 KV cache 是单实例 CUDA 状态，必须串行执行；异步只负责
   请求接入、流式分发和等待，不改变模型执行的串行性。
7. **流式 detokenizer 为什么不能逐 token decode？**
   UTF-8 字符可能跨多个 token；单独 decode 会先产生 `�`。累计 decode 并 hold
   back 尾部 replacement char，才能保证文本稳定。
8. **取消后 KV 怎么回收？**
   `scheduler.abort` 从 waiting/running 移除请求，`BlockManager.deallocate`
   递减 block refcount，归零后回到 free/LRU 堆；in-flight 列表也同步剔除。
