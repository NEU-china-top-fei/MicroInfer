# P5：n-gram / draft-model 投机解码

P5 实现两条 greedy draft 通路：

- **prompt-lookup n-gram**：不依赖额外模型，从历史 token 中找候选 continuation；
- **独立 draft model**：可选的 HF causal LM + per-sequence 增量 KV cache。

两者都由 target model 一次性验证，减少 greedy decode 的 target forward 次数。

当前实现是 **opt-in、greedy-only**，默认关闭；重点验证正确性、KV 回滚和
可观测指标，不把收益说成通用加速。

## 1. 为什么先用 n-gram

n-gram lookup 不需要 draft model：

- 从 prompt + 已生成 token 建 3-gram 索引；
- 用最后 3 个 token 找之前的相同 3-gram；
- 把该位置之后的 1–8 个 token 作为 draft。

它特别适合：

- 复制/改写类 prompt；
- 重复列表、模板、代码补全；
- 输出中有大量自重复的文本。

对随机、创造性输出通常没有 draft 或 draft 很快被拒绝，收益接近 0，甚至因为
验证开销略慢。

## 2. 设计

### 2.1 NgramSpeculator

`microinfer/engine/speculative.py`：

```text
propose(token_ids):
    key = token_ids[-ngram:]
    for i from len-ngram-1 down to 0:
        if token_ids[i:i+ngram] == key:
            return token_ids[i+ngram:i+ngram+max_drafts]
```

- 跳过当前 occurrence，避免直接返回自己；
- 默认 3-gram、最多 8 个 draft；
- 纯 Python 扫描，适合 1–4K token；超长上下文可后续换增量索引。

### 2.2 触发条件

只有同时满足才进入 speculative step：

- `EngineConfig.use_speculative=True`；
- 所有 running 请求都是 greedy；
- waiting 队列为空（避免和 mixed prefill 组合）；
- 每个 running 请求都能拿到至少 1 个 draft；
- KV 有足够 block 容纳 draft。

任一条件不满足就回退普通 scheduler，不影响其他请求。

### 2.3 验证

`Runner.run_verify` 把 `[last_token] + drafts` 当作 packed prefill：

- query 长度 = `1 + len(drafts)`；
- context 长度包含已有 prefix 和 draft；
- 返回 **所有 query 的 logits**（普通 decode 只保留最后一个）；
- prefill 仍 eager，decode 的 graph/compile 不受影响。

### 2.4 接受策略：最长前缀 + 普通 decode 生成下一 token

1. 对每个 draft 位置取 target argmax；
2. 保留最长可接受前缀；
3. 提交这些 draft，然后 **用普通 decode 再生成下一个 token**。

验证 logits 只用于判断 draft 是否与 target 一致，不直接作为输出 token。这样 correction 路径不会直接采用 verification 的 logits；被拒绝的 draft 不会污染
token 序列，也不会被后续 attention 读取。测试 workload 上输出与 greedy baseline
一致。verify（prefill layout）和 decode（graph/Triton/FA）在 bf16 下的极小数值差
在 near-tie 位置仍可能改变某个 draft 的接受，这是 greedy spec 的已知边界。

### 2.5 KV 回滚与提交

验证前把 draft 临时追加到 `Sequence.token_ids`：

```text
base = len(seq)                 # includes last sampled token
cached_before = base - 1
append drafts
num_scheduled_tokens = 1 + len(drafts)
```

验证写入这些位置的 K/V。提交 `count` 个接受 draft 时：

- 保留 `token_ids[:base+count]`；
- 发布已接受 token 覆盖的 full-block hash；
- `num_cached_tokens = base+count-1`，故意把最后一个 accepted draft 留作
  “未 cache”，让普通 decode 重写该位置并采样下一个 token；
- 回收为 draft 多分配的 block（`BlockManager.trim`）；
- 如果 accepted 已填满 `max_tokens`，直接以 `length` 结束；
- 否则调用普通 scheduler decode，生成下一个 token。

拒绝位置（未进入最长前缀）的 stale KV 不读取，后续写入会覆盖。

## 4. 性能

### 4.1 n-gram 结果

环境：RTX 4060 Laptop / Qwen3-0.6B bf16 / block16 / CUDA Graph / greedy。

测试 prompt 是一个重复句子：

```text
Repeat exactly the following sentence, then continue repeating it:
The quick brown fox jumps over the lazy dog. ×3
```

| 指标 | baseline | speculative |
| --- | ---: | ---: |
| output tok/s | 117.3 | **261.8** |
| median wall | 272.8 ms | **122.2 ms** |
| spec steps | 0 | 16 |
| drafts / accepted | 0 / 0 | 108 / 108 |
| acceptance rate | — | **100%** |
| 输出一致 | — | **是** |

加速约 **2.23×**。原因是 prompt 和输出高度重复，n-gram draft 几乎全部命中；
每个 spec step 仍保留一次普通 decode 来生成下一 token，换取输出一致性。

非重复 prompt（`Hello, my name is`）：

| 指标 | baseline | speculative |
| --- | ---: | ---: |
| output tok/s | 117.8 | 111.6 |
| acceptance rate | — | 0% |
| 输出一致 | — | 是 |

此时 verification 没有收益，反而有约 5% 开销。因此 `use_speculative` 默认关闭，
应按 workload 开启。

### 4.2 Draft model 结果

draft model 有两条实现：

- `DraftModelSpeculator`：HF causal LM + per-sequence 增量 KV cache；
- `NativeDraftSpeculator`：把 Qwen checkpoint 按层裁剪成更小的 draft，放进
  MicroInfer 的 `ModelRunner`，使用与 target 相同的 paged KV、packed weights、
  block16 Triton decode 和 CUDA Graph；draft 提议按 batch 合并。

测试：target Qwen3-1.7B，6 个真实文本 prompt 并发 4 路，output 32，
block16、512 KV blocks、CUDA Graph：

| 方案 | max_drafts | baseline tok/s | spec tok/s | speed | acceptance | 输出一致 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| HF draft 0.6B | 1 | 157.1 | 81.8 | 0.52× | 71.4% | 是 |
| HF draft 0.6B | 4 | 156.2 | 79.3 | 0.51× | 60.0% | 否 |
| native full 0.6B | 1 | 158.5 | 102.9 | 0.65× | 71.4% | 是 |
| native full 0.6B | 4 | 159.1 | 109.4 | 0.69× | 60.0% | 否 |
| native pruned 20/28 | 4 | 159.6 | 74.4 | 0.47× | 9.6% | 是 |
| native pruned 8/28 | 4 | 159.9 | 68.7 | 0.43× | 0.0% | 是 |

解读：

- 把 draft 从 HF eager 换成 MicroInfer native runner 后，0.6B draft 的吞吐从
  0.51× 提升到 **0.69×**，说明 paged KV/Graph/batch 确实有效；
- 但 target 1.7B 在 batch4 下已经很快，0.6B draft 的逐 token 成本仍然吃掉收益；
- **更小的层裁剪 draft 不划算**：8 层、20 层 draft 的接受率跌到 0–10%，节省的
  target step 抵不过额外 verify/draft；
- 真实文本接受率约 60–71%；max_drafts=4 时仍有 1/6 prompt 在 near-tie 位置
  出现 token 分歧，max_drafts=1 在测试中一致；
- 结论：**优化 draft 本身能缩小差距，但在这张 8GB 卡 + 0.6B/1.7B 组合上仍不能
  超过 baseline**。要获得收益，需要 0.1–0.3B 且与 target 对齐良好的蒸馏 draft，
  或更大的 target（7B+）让 draft 相对成本下降。

### 4.3 对 target 和 draft 都做 per-op compile

`--compile-ops` 把 RMSNorm+residual、SwiGLU、RoPE 分别 `torch.compile`，再和
CUDA Graph 一起使用（全图 `use_compile` 仍与之互斥）：

- target 1.7B 的 6 prompt/4 并发 baseline 从 **159 → 178 tok/s**；
- native draft 0.6B 的 spec 从 **109 → 123 tok/s**；
- 两边都受益，但 draft 成本仍然存在，spec/baseline 仍约 **0.68×**；
- 首次编译成本约 13 s（1.7B target），之后稳态。

所以 per-op compile 解决了 target/draft 的“算子融合”问题，但没有改变 draft
模型本身相对 target 仍然太贵的事实。

## 6. 限制与下一步

- 只支持 greedy；temperature 的 rejection sampling 尚未实现。
- 已接受前缀后仍要一次普通 decode；接受率低时 verify 的 forward 是纯开销。
- 只有 no-waiting 时启用，未和 P4 的 mixed prefill 组合。
- `speculative_min_margin=0.5` 会拒绝 top-1/top-2 过近的 draft，降低近 tie 风险，
  但不能视为绝对保证。
- verification 与 decode 的 kernel 数值路径不同，near-tie 时 draft 接受仍可能与
  纯 decode 基线有极少数差异；输出一致性测试覆盖了重复和随机 prompt。
- n-gram 扫描是 O(context_len)，超长上下文需要增量索引。
- draft model 已有 HF 与 native（paged KV/Graph/batch）两版；native 0.6B 仍为 0.69×，
  8/20 层裁剪接受率跌到 0–10%。需要更小且对齐的蒸馏 draft，或更大 target。
- 可进一步做 tree speculation、多个 draft 候选和 acceptance-aware scheduling。

## 7. 面试追问

1. **投机解码为什么能加速？**
   draft 提议多个 token，target 一次 forward 验证多个位置；接受 d 个 draft 时，
   原本 d+1 次 decode forward 变成 1 次 verify + 1 次正常 decode。
2. **n-gram draft 的命中率由什么决定？**
   prompt/输出重复度；复制、模板、代码和列表类文本高，随机创作低。
3. **为什么 verify 的 logits 只决定 draft，不直接输出 correction？**
   verify 走 prefill attention，decode 走 graph/Triton/FA decode，bf16 数值路径
   不同；接近 tie 时 argmax 可能变化。提交 accepted draft 后用普通 decode 采样，
   保证 greedy 输出一致。
4. **KV 如何回滚？**
   draft 临时追加到 token_ids；拒绝时截断 token_ids、把 `num_cached_tokens` 恢复
   到 base-1，并 trim 多分配的 block。stale KV 不读取，后续写入覆盖。
5. **为什么 spec 不在 waiting 非空时启用？**
   避免把 verification 和 mixed prefill 的调度/attention 布局混在一起；先保证
   正确性和可解释性，后续再做统一调度。
6. **当前策略的代价？**
   每个 spec step 都有一次 verify + 一次普通 decode；低接受率时 verify 是纯开销，
   适合高重复、可预测的输出。
7. **如何扩展 temperature 采样？**
   对每个 draft 用 target 分布做拒绝采样，接受概率 `min(1, p_target/p_draft)`，
   拒绝时从修正分布采样；需要 draft 概率和随机数，当前未实现。
