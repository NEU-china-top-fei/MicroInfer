# P3：任意 block size 的 Attention 快路径

P1/P2 之后，MicroInfer 的 decode 已经能走 `torch.compile` 或 CUDA Graph。
但 attention 仍有一个隐含约束：**FlashAttention 的分页 kernel 要求
`block_size % 256 == 0`**。项目默认 `block_size=16`，于是默认配置会静默退回
逐请求 Python 参考实现，吞吐只有 fast path 的三分之一左右；CUDA Graph 也会直接拒绝
捕获。

P3 的目标是把“调度/KV 管理使用的 block size”和“attention kernel 支持的 block size”
解耦：

- 任意 2 的幂 block size（16/32/64/128/256）都有可用的 decode kernel；
- 小 block 的 prefill 不再走 Python 循环，而是 gather 后调用 varlen FlashAttention；
- 小 block 也能被 CUDA Graph 捕获；
- 与参考实现的数值和真实 Qwen3-0.6B 的 greedy token 对齐。

## 1. 问题定位

FlashAttention 2 的 paged kernel 为了做连续访存和向量化，要求 physical block
覆盖 256 个 token。`block_size=16` 时 `flash_attn_with_kvcache` 不接受该布局，
`flash_attn_varlen_func` 的 `block_table` 参数也有同样限制。

原实现的回退链是：

```text
decode:
  block_size % 256 == 0 -> flash_attn_with_kvcache
  否则                  -> Python for-request reference（每层、每请求）

prefill:
  block_size % 256 == 0 -> flash_attn_varlen_func(block_table=...)
  否则                  -> Python for-request reference
```

参考实现会逐请求 `einsum`/`softmax`/`einsum`，并且每层都做一次 Python 循环。
P0 的 `block_size=16` 基线只有 33.5 tok/s（单流）、120.2 tok/s（batch-8），
长 prefill TTFT 662 ms。

P3 把回退链改成：

```text
decode:
  block_size % 256 == 0 -> FlashAttention paged decode
  否则 Triton 可用      -> triton_paged_decode
  否则                  -> reference

prefill:
  block_size % 256 == 0 -> FlashAttention paged varlen
  否则                  -> gather paged KV -> FlashAttention varlen
  否则                  -> reference
```

## 2. Triton paged decode kernel

文件：`microinfer/layer/triton_paged_attention.py`

### 2.1 并行划分

```text
grid = (num_requests, num_q_heads)
program(request, head):
    kv_head = head // (num_q_heads // num_kv_heads)
    每次处理 BLOCK_N 个逻辑位置，跨 block 时向量化查 block_table
    对每个 tile 做 online softmax
```

一个 program 负责一个 query head 的完整 head_dim 向量，因此：

- 不需要跨 program 做 reduction；
- GQA 通过 `kv_head = q_head // group_size` 复用 KV head；
- grid 很小，decode 的 host 端 launch 成本低，适合 CUDA Graph；
- tile 跨多个物理块时，用一次向量化 `block_ids` 查询构造 K/V 地址，
  避免逐 block 循环。

### 2.2 Online softmax

每个 tile（eager/CUDA Graph 下 `BLOCK_N=128`）做一次 online softmax：

```text
scores = (K_tile @ q) * scale
new_max = max(running_max, max(scores))
alpha = exp(running_max - new_max)
P = exp(scores - new_max)
running_sum = running_sum * alpha + sum(P)
acc = acc * alpha + P @ V_tile
running_max = new_max
```

最后 `acc / running_sum`。整个累加使用 FP32：

- `q`、`K`、`V` 在 load 后 `.to(tl.float32)`；
- `scores`、`P`、`acc` 都是 FP32；
- 输出写回 FP16/BF16/FP32。

tile 大小是性能关键：更大的 tile 把 4096-token context 的循环次数从 256 降到 32。
但 `torch.compile` 下 Inductor 重新生成 kernel，128-tile 明显更慢（推测与寄存器
压力有关），所以 `triton_paged_decode` 在 `torch.compiler.is_compiling()` 时用
`BLOCK_N=32`，eager/CUDA Graph 用 128。两者都经过同一组数值测试。

这一点和参考实现的口径一致：半精度 QK 可能在 softmax 前溢出，不能直接用 FP16
累加。测试 `test_triton_paged_decode_matches_reference` 覆盖 FP32/FP16/BF16。

### 2.3 支持范围

- `block_size`：任意 2 的幂（16/32/64/128/256）；
- `head_dim`：任意 2 的幂（Qwen3-0.6B 为 128）；
- dtype：FP16/BF16/FP32；
- GQA：`Hq % Hkv == 0`；
- block table 可以是乱序物理块，也可以有 `-1` padding；kernel 只读取
  `ceil(context_len / block_size)` 个有效块。

不满足时 wrapper 抛出明确错误；`paged_attention_meta` 只在满足条件时分派到它，
否则继续走 reference。

### 2.4 为什么能进 CUDA Graph

Triton kernel 本身只是普通 CUDA kernel。只要在 capture 前完成 JIT 编译和
allocator 预热，capture 阶段看到的就是一次 `cuLaunchKernel`。

Runner 的 capture 流程本来就有 side-stream warmup：

1. 用一个假 metadata 在 side stream 上跑一遍 eager decode；
2. 这一步触发 Triton JIT、caching allocator 和 cuBLAS workspace 初始化；
3. `torch.cuda.synchronize()`；
4. 用全新的 metadata 在 capture stream 上捕获 graph。

`test_graph_decode_with_triton_small_blocks` 用 `block_size=16`、batch=3
（padding 到 bucket=4）验证 graph 与 eager 的 token 完全一致。

### 2.5 与 torch.compile 的协同

P1.5 在 `block_size=256` 上只编译 decode 时，FlashAttention 的 pybind 调用
`flash_attn_2_cuda.PyCapsule.fwd_kvcache` 会让 Dynamo 每层 graph break：

```text
block256 compile: frames=13, ok=13, graph_break=7, unique_graphs=11
block16  compile: frames=1,  ok=1,  graph_break=0, unique_graphs=1
```

原因是我们自己的 Triton kernel 是普通 Python 函数 + Triton launch，Dynamo 能追踪
并把 `_paged_decode_kernel` 一起交给 Inductor；FA 的 C++ 扩展则是 opaque call。
因此小 block 的 compile 反而能得到**一个完整的 decode graph**：

| workload | bs16 compile | bs16 graph |
| --- | ---: | ---: |
| single-short | **126.9** | 112.5 |
| batch8-short | **710.7** | 676.9 |
| batch32-mixed | 847.0 | **914.3** |
| shared-prefix | 619.1 | **699.3** |
| long-prefill | 59.7 | **65.0** |

compile 在单流/batch8 上比 graph 高 5%–13%，因为它同时做了算子融合；graph 在
batch32/长上下文上更高，因为大 tile 的 kernel 不被 Inductor 的寄存器分配拖累。
两者仍然互斥。检查 Dynamo 行为的命令：

```bash
TORCH_LOGS=graph_breaks python -m bench.bench_offline \
  --model /path/to/Qwen3-0.6B --engine microinfer --workloads single-short \
  --runs 1 --warmup 1 --block-size 16 --num-blocks 1024 --use-compile
```


## 3. 小 block 的 paged prefill

文件：`microinfer/layer/paged_attention.py`

### 3.1 Gather + varlen FlashAttention

`flash_attn_varlen_func` 不接受小 block 的 `block_table`，但它接受连续的
`[total_k, Hkv, D]` K/V。于是 prefill 走：

```text
for each request:
    blocks = block_table[:ceil(context_len / block_size)]
    K = key_cache.index_select(0, blocks).reshape(-1, Hkv, D)[:context_len]
    V = value_cache.index_select(0, blocks).reshape(-1, Hkv, D)[:context_len]
K_packed = cat(K); V_packed = cat(V)
flash_attn_varlen_func(
    q, K_packed, V_packed,
    cu_seqlens_q, cu_seqlens_k,
    causal=True,
)
```

关键点：

- `index_select` 按物理块号取 K/V，逻辑顺序由 block table 决定；物理块可以乱序；
- 每个请求只取有效 token，不带 block 尾部 padding；
- `cu_seqlens_q/k` 来自 metadata，前缀复用和 chunked prefill 的
  `q_len < context_len` 也成立；
- `causal=True` 使用 bottom-right 对齐，正好对应“prefix + 当前 chunk”的可见性；
- gather 每层执行一次，临时 K/V 只在该层 attention 期间存活。prefill 的 GEMM
  占主导，这份拷贝相对较小；它的代价主要体现在 `shared-prefix` 的 TTFT 上。

### 3.2 为什么不用逐请求 SDPA

早期实现虽然叫 gather，实际仍对每个请求单独调用 SDPA，并且在 FP32 中计算。
它避免了 Python reference 的最慢路径，但仍然是：

- 每请求一次 kernel launch；
- 每层一次 Python 循环；
- 显存中同时存在多份 4D Q/K/V。

改成“一次 gather + 一次 varlen FlashAttention”后，prefix/chunked prefill 的
Python 循环和 kernel 数都下降，且和 `block_size=256` 的语义一致。无前缀 prefill
仍走 `CachedAttention` 的 direct varlen 路径，不经过 paged cache。

### 3.3 回退

当 CUDA、dtype、head_dim 或 FlashAttention 不满足时返回 `None`，继续走
`_paged_attention_reference`。CPU 测试和 FP32 小张量测试仍然覆盖 reference 路径。

## 5. 性能

环境：RTX 4060 Laptop 8 GB / Qwen3-0.6B bf16 / cold cache / 3 次运行中位数。
`block_size=16` 使用 `num_blocks=1024`，`block_size=256` 使用 `num_blocks=64`，
两者 KV 容量都约 1.79 GB。

| workload | bs16 eager | bs16 compile | bs16 graph | bs256 graph |
| --- | ---: | ---: | ---: | ---: |
| single-short | 63.4 | **126.9** | 112.5 | 110.3 |
| batch8-short | 469.4 | **710.7** | 676.9 | 679.1 |
| batch32-mixed | 847.8 | 847.0 | 914.3 | **918.0** |
| shared-prefix | 482.1 | 619.1 | **699.3** | 690.2 |
| long-prefill | 50.0 | 59.7 | **65.0** | 64.1 |

单位：output tok/s。详细 TTFT/TPOT：

| workload | bs16 graph TTFT | bs16 graph TPOT | bs256 graph TTFT | bs256 graph TPOT |
| --- | ---: | ---: | ---: | ---: |
| single-short | 16.8 ms | 8.6 ms | 18.1 ms | 8.8 ms |
| batch8-short | 67.8 ms | 10.0 ms | 66.9 ms | 10.0 ms |
| batch32-mixed | 678.3 ms | 14.3 ms | 669.5 ms | 14.4 ms |
| shared-prefix | 34.9 ms | 10.7 ms | 26.1 ms | 11.1 ms |
| long-prefill | 166.9 ms | 10.6 ms | 166.3 ms | 10.8 ms |

4K context（4000-token prompt + 8 个输出，graph）：

| block size | output tok/s | TTFT | TPOT |
| --- | ---: | ---: | ---: |
| 16（Triton） | 16.2 | 405 ms | 12.6 ms |
| 256（FA） | 16.4 | 404 ms | 12.1 ms |

### 解读

1. **单流和 batch-8 不再有惩罚，compile 甚至更快。** block16 compile 单流 126.9、
   batch8 710.7，分别比 bs256 graph 高 15% 和 5%；block16 graph 也基本追平
   （112.5 vs 110.3）。Triton kernel 的 grid 足够小，launch 被消除后不再是瓶颈，
   而 compile 还能继续融合 GEMM/elementwise。
2. **高 batch/长上下文已经追平。** 128-token tile 把长 context 的循环次数降下来后，
   bs16 graph 在 batch32（914.3 vs 918.0）、shared-prefix（699.3 vs 690.2）、
   long-prefill（65.0 vs 64.1）都与 bs256 graph 持平；4K context 的 TPOT
   只差 4%。不再需要为了吞吐把 block size 固定成 256。
3. **shared-prefix 的 TTFT 仍有差距。** block16 需要把 512-token 前缀 gather 成
   连续 K/V；block256 的 paged varlen kernel 直接读 cache。TTFT 34.9 vs 26.1 ms，
   但 decode 更快，最终吞吐反而略高；相对 P0 的 662 ms 已经不是一个量级。
4. **显存几乎不变。** bs16 graph 峰值 3.4 GB，与 bs256 的 3.44 GB 同量级；
   小 block 的价值是分配粒度更细、内部碎片更少，而不是省掉 KV 总量。
5. **相对 P0 的提升是数量级的。** P0 `block_size=16` 单流 33.5、batch8 120.2、
   long-prefill 20.0 tok/s；P3 graph 分别达到 112.5 / 676.9 / 65.0。

### 结论

- 默认 `block_size=16` 不再需要“为了性能改成 256”；
- 单流/中低 batch 优先考虑 `block_size=16` + compile（完整 decode graph）；
- 高 batch/长上下文用 `block_size=16` + CUDA Graph，已经与 FA/block256 持平；
- 小 block 的细粒度 KV 管理不再有吞吐代价。

## 7. 限制与下一步

- kernel 已经有跨 block tile，但没有 split-K。4K context 下 TPOT 与 FA 只差 4%，
  当前不需要 split；如果上下文继续变长或并发更高，可以按 context 长度做 split，
  再用第二个 reduction kernel 合并。
- GQA 的 K/V 仍按 query head 重复读取；按 KV head 分组、一次计算
  `group_size` 个 query head 可以把 K/V 读取量再降一个 group_size。
- compile 下 Inductor 重新生成 kernel，128-tile 明显更慢，因此用 32-tile；
  这是当前 kernel 在两种执行模式下的取舍，不是语义差异。
- prefill 的 gather 是额外拷贝；如果后续实现自己的 paged varlen kernel，可以
  省掉这份临时 K/V。
- CUDA Graph 仍只覆盖 decode；prefill 继续 eager。
- P4 会把 attention 快路径放进异步引擎和 OpenAI 兼容服务，测 P99 TTFT/TPOT，
  而不是只看离线吞吐。

## 8. 面试追问

1. **为什么 FA 的 paged kernel 要求 256 的 block？**
   连续物理块可以摊薄 block table 查找，并让 K/V 以更大的 tile 进入 shared
   memory；小 block 会让每个 tile 的有效 token 太少，kernel 内部会做大量
   padding/分支。实现上直接把 256 作为约束，而不是为所有尺寸维护多套 tile。
2. **Triton kernel 为什么用 FP32 累加？**
   QK 点积和 softmax 的指数在半精度下容易溢出或丢精度；FP32 累加与参考实现
   一致，代价是寄存器/shared memory 占用更高。
3. **online softmax 的数值稳定性来自哪里？**
   每处理一个 tile 都用当前最大值重标定：旧的 `acc` 和 `sum` 乘
   `exp(old_max - new_max)`，保证指数不会超过 1。
4. **GQA 在 kernel 里怎么处理？**
   `kv_head = q_head // (Hq/Hkv)`；每个 query head 独立一个 program，读取同一个
   KV head。这样实现简单，但会重复读 K/V；进一步优化是按 KV head 分组。
5. **为什么 prefill 不直接对小 block 用 paged FA？**
   FA 的 varlen 接口也要求 block table 的 block size 为 256。gather 成连续
   K/V 后可以复用标准 varlen kernel，代价是一层一次拷贝。
6. **Triton kernel 如何与 CUDA Graph 共存？**
   capture 前在 side stream 上 warmup，触发 JIT 和 allocator；capture 时只记录
   kernel launch。block table/context lens 是固定 device buffer，replay 时更新
   内容即可。
7. **为什么 compile 和 eager/CUDA Graph 用不同 tile？**
   eager/CUDA Graph 直接用我们写的 kernel，128-tile 的循环次数少、吞吐高；
   compile 时 Inductor 会重新生成 kernel，128-tile 明显更慢（推测与寄存器压力
   有关），32-tile 更快。用 `torch.compiler.is_compiling()` 在 trace 期选择，
   属于实现细节，不影响数值语义。
